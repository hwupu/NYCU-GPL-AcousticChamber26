UI components — as built, with Unity names (v3, PB-07c)

This page mirrors the screens the code builds at run time (scheme B; 1 u = 1 pt, at 2 m 1 u = 2 mm). The hover tag reads code that builds it · GameObject name (e.g. UiKit.Row · Row Playground: a list row made by UiKit.Row whose label is "Playground"); the bar at the bottom adds what the component is. Every element carries the GameObject name the runtime gives it: hover an element and the bar at the bottom shows its path as it appears in the Unity Hierarchy during Play (Ctrl+click copies the path). Use these names when we talk about a part ("Row Playground › Sub"). Sizes and positions are close, not exact; the code is the reference. Section 0 lists the vocabulary.

0. Vocabulary: component → code → GameObject name

Where to look in the Hierarchy (Play mode): UI › <canvas>. The chamber scene's canvas is Chamber Menu, the Hall's is Hall. Screens are children of the canvas: the menu's Window holds a stack of Page … objects; sheets and dialogs, participant screens and the cue text are added next to the Window.

An info row switches between the two at run time (Parameters: the Sub shows the description, or "Default: 2" when edited, and disappears when there is neither).

1. Buttons and states

Hierarchy by fill. Prominent: the one main action of a screen. Gray: a secondary action that needs a visible target. Borderless: everything else (back, cancel, keys, list actions). Destructive: red fill only on a final confirmation; elsewhere red text. Normal → hover → pressed get brighter. Every button is a GameObject with a child Label.

2. Chamber menu (canvas Chamber Menu)

As built after PB-20: Study ID pad at the left; Start and Debug at the right, sharing the pad's top edge; the group is centered vertically between the header and the status band. Under the buttons, one line each when needed: Volume ("Audio level: 10 (target 8)", red when off target), Preset ("Preset: Custom"), Unfinished ("Unfinished: S0005"). Status at the bottom. Start: an ID with an unfinished session asks Resume / Start new / Back (Dialog); the volume is read from the headset (the Volume Step sheet stays in code, off). Y opens the Stop dialog while a run is going.

During a trial the window is hidden: the Stop Dialog appears alone over the scene.

3. Main Hall (canvas Hall)

2-column grid of Card <id> in the scroll list Chambers; the "N unfinished" pill is Unfinished on the Cover. Only the Template exists today; the gray cards show how more chambers would sit.

Main Hall

4. Debug pages (GPL.DebugBench, on the chamber menu's Window)

Debug opens Page Debug on the same page stack; Parameters, Presets and Log files push their pages on top. The Template's parameters are shown. Both row layouts appear here: one-line rows (Practice trials, Blocks, …) and two-line rows (Response timeout with its description; any edited value shows "Default: …" as its Sub).

Pages (all children of Window)
Page Debug: Run (Run experiment trials · Practice trial) · Parameters (Playground ›, Presets ›) · Data (Log files ›) · Status
Page Parameters: Action Revert · one group per parameter group · Save (Save as Custom)
Page Presets: Default, Custom (✓ = active) → sheet Preset <name>: Make active · Delete
Page Log files: Action Delete all · Files (Row <file> with Delete) → Dialog

5. Participant screens (GPL.Protocol, Template order)

Built on the same canvas while a session runs (the menu window is hidden). Each screen is its own window named after it; the cue text Protocol Cue has no panel, so the world (fixation dot) stays visible. Text follows the participant language (toolbar). Two layouts: the Slide layout (recenter and instruction slides: title row, image, ← Back / Next →, where the buttons name the slide they lead to, and the last instruction slide says Continue) and the Message layout (language choice, block break, thanks; the Protocol screen for the experimenter adds the slide title row). No screen waits for A; A is only the trial response.
